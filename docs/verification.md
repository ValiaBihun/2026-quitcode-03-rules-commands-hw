## Task B — чи бачить інструмент AGENTS.md

- Інструмент і версія: Claude Code (desktop app), модель Opus 5
- Що було до: `CLAUDE.md` містив markdown-**посилання** `[AGENTS.md](./AGENTS.md)`.
  Посилання не є імпортом — Claude Code не завантажує файл за ним, агент бачить
  лише рядок тексту. Це і був баг стартера.
- Що зроблено: у `CLAUDE.md` поставлено **імпорт окремим рядком** — `@AGENTS.md`;
  нижче лишилось тільки специфічне для Claude Code (перелік правил, команд, хук).
  `AGENTS.md` переписано з «пиши якісний код» на 58 рядків конкретики.
- Як перевірити: нова сесія → які файли інструкцій проєкту фактично завантажено
  (`/context` → **Memory files**); і контрольне питання агентові без відкриття файлів.
- **Результат (нова сесія, 20.09.2026):** завантажено рівно **три** файли
  інструкцій проєкту:

  ```
  CLAUDE.md                      (project instructions, checked into the codebase)
  AGENTS.md                      (project instructions, checked into the codebase)
  .claude/rules/do-not-touch.md  (project instructions, checked into the codebase)
  ```

  `AGENTS.md` потрапив у контекст **не сам по собі** — Claude Code читає лише
  `CLAUDE.md`, а далі йде по рядку `@AGENTS.md`. До виправлення на його місці було
  markdown-посилання, і файл не завантажувався. Тобто імпорт працює, і це видно
  на фактичному вмісті контексту, а не з опису.

- Контрольне питання агентові в тій самій сесії («які правила проєкту вже є в
  тебе в контексті? файли не відкривай») — відповів переліком із `do-not-touch.md`
  (захищені зони, процедура зупинки, заборона `--write-lock`) і семи однорядкових
  правил з `AGENTS.md`, і сам зазначив:

  > «Деталі шарів, публічного API ядра й конвенцій коду/тестів у контексті
  > відсутні — вони в `architecture.md` і `conventions.md` з
  > `paths: app/src/**/*.ts`.»

## Task A — режими застосування правил

Та сама перевірка з нової сесії підтверджує пункт 3 умови Task A — режими обрано
свідомо, і вони справді працюють:

| Правило | Режим | Чи в контексті на старті | Чому так і треба |
|---|---|---|---|
| `do-not-touch.md` | без frontmatter | **так** | захист має діяти в кожній сесії, зокрема в тих, що не торкаються `app/src/**` |
| `architecture.md` | `paths: app/src/**/*.ts` | ні | підтягнеться при роботі з кодом застосунку |
| `conventions.md` | `paths: app/src/**/*.ts` | ні | те саме — інакше це зайвий контекст у кожній сесії |

**Друга половина доказу — правила за `paths` таки підтягуються.** Під час прогону
`/analyze-error` (нижче) агент прочитав `app/src/sync/state.ts`, і обидва правила
з `paths: app/src/**/*.ts` автоматично зайшли в контекст — без `@`-згадки й без
відкриття їхніх файлів. Тобто режим працює в обидва боки: у сесії без коду
застосунку правил немає, у сесії з кодом вони з'являються самі.

Це і є різниця, за яку рубрика знімає бали: якби всі три були always-on, агент
тягав би конвенції коду в сесію про CI чи документацію.

## Task C — прогони команд

### `/analyze-error materials/error-log.txt`

- Виклик: `/analyze-error materials/error-log.txt` — **справжній прогін через `/`**
  у сесії, де команда вже зареєстрована (20.09.2026).
- **Чи підставився `$ARGUMENTS`: так.** У завантаженому тілі команди рядок «Ціль»
  прийшов уже розкритим:

  ```
  **Ціль:** materials/error-log.txt
  ```

  Тобто запасний варіант із шаблону («якщо плейсхолдер не підставився — візьми
  ціль із тексту після назви команди») у Claude Code не знадобився.
- **Побічне спостереження:** щойно агент прочитав `app/src/sync/state.ts`,
  у контекст самі зайшли `architecture.md` і `conventions.md` — ті, що з
  `paths: app/src/**/*.ts`. Це підтверджує режим прив'язки за шляхами на практиці.
- **Тригер:** `2026-09-10T00:02:37Z` — нічний бекап забив диск
  (`disk usage /srv/lead-sync/data: 97%`, о 00:05 — 100%). О 00:05 і 00:10 прогін
  падає з `ENOSPC` у `saveState` (`app/src/sync/state.ts:21`), викликаному з
  `runSync` (`app/src/sync/run.ts:18`).
- **Корінна причина:** `app/src/sync/state.ts:13–17` — `loadState()` обгортає
  `JSON.parse(readFileSync(...))` у `try/catch`, і в `catch` **мовчки повертає**
  `INITIAL_STATE` з `lastSyncedAt: "1970-01-01T00:00:00.000Z"`.
  Механізм: `writeFileSync` спершу обрізає файл, а вже потім пише, тож падіння на
  `ENOSPC` лишило `data/sync-state.json` порожнім/побитим. Після цього кожен
  наступний запуск читає порожній файл, тихо відкочує курсор у 1970 рік і вважає
  **всі ~1300 лідів** новими — звідси дублікати в Slack і в таблиці.
- **Чому це не тригер:** о `00:13:48` ops звільнили диск (`disk usage: 41%`), а
  дублікати йшли ще до `09:14` — **дев'ять годин** після зникнення тригера.
  Місце на диску не було тим, що тримало систему зламаною.
- **Чому воно не полагодилось саме (друга половина механізму):** `runSync` пише
  новий `lastSyncedAt` **лише в кінці** прогону (`app/src/sync/run.ts`, останній
  `saveState`). Розсилка ~1300 лідів × 2 інтеграції впирається в ліміт Slack
  (`HTTP 429` о 00:18) і планувальник вбиває процес на 4м30с
  (`run exceeded 4m30s limit, worker process killed (SIGKILL)`) — **до** того
  запису. Стан не лагодиться ніколи, і цикл самопідтримується кожні 5 хвилин.
- **Яку конвенцію порушено:** «Зовнішнім даним не довіряємо» — будь-який JSON лише
  через `parseJson(text, guard)`, а невалідний JSON це `Result{ok:false}`, який
  видно в журналі; тихий дефолт заборонений. Цей самий рядок ловить і
  `check:rules`: `src/sync/state.ts  json-via-parse  line 14`. Це **останнє**
  порушення, що лишилось у проєкті.
- **Тест, що відтворює:** `app/src/sync/state.test.ts` — записати у тимчасовий файл
  порожній рядок (як після обірваного `writeFileSync`) і викликати `loadState(path)`.
  Зараз повертає `{ lastSyncedAt: "1970-01-01T00:00:00.000Z" }` мовчки; очікування —
  помилка назовні, а не відкат курсора. Рівнем вище: `runSync` з побитим станом і
  трьома старими лідами зараз звітує `pending: 3` замість `pending: 0`.
- **План виправлення (не застосований):** `loadState` повертає `Result<SyncState>`
  через `parseJson` з guard на `{ lastSyncedAt: string }`; `runSync` на
  `ok: false` **зупиняє прогін** з помилкою в журналі замість розсилки з нуля;
  окремо — зберігати курсор інкрементально, щоб убитий прогін не втрачав прогрес.
  Обидва файли в `app/src/sync/`, ядро чіпати не треба.
- **Чи зупинився там, де сказано в Stop:** так. Після звіту агент зупинився й
  попросив підтвердження. `git status --short` під час прогону — порожній, файл
  `state.test.ts` не створювався. Порушення `json-via-parse` у `state.ts:14`
  лишилось у `check:rules` навмисно — як доказ, що звіт не перетворився на
  самовільний фікс.
- **Acceptance criteria команди — усі п'ять виконані:** названо файл і рядок
  (`state.ts:13-17`, механізм через `state.ts:21` і `run.ts:20/36`); доказ із
  хронології (тригер зник о 00:13:48, симптом тривав до 09:14:30); названо
  конвенцію; описано тест і чому він падає; робоча тека чиста.
- **Чи знадобилась ітерація над командою:** ні. Крок 3 «відріж тригер від причини»
  з трьома контрольними питаннями (чи тривав симптом після зникнення тригера;
  який рядок вирішив працювати з побитим станом; що мало б статися за правилами)
  вивів на причину з першого прогону. Без цього кроку природна відповідь —
  «закінчилось місце на диску», тобто тригер.

підтвердження людини. Числа прогону нижче перевіряються з git:
`git show origin/main:app/src/integrations/sheets-append.ts` містить рівно сім
збігів із шаблонами `check:rules`, у поточному файлі їх нуль.
